## 2\. Поднятые сервисы — и почему именно они

Перечисли, что реально поднял (проверь через `docker ps`), и обоснуй выбор каждой технологии.

| Сервис | Роль в стеке | Почему именно он (а не альтернатива) |
| :---- | :---- | :---- |
| MinIO | S3-совместимое объектное хранилище (сюда физически падают parquet-файлы) | Позволяет хранить данные локально в Docker без привязки к облаку, обеспечивает нативную поддержку Iceberg и даёт веб\-консоль для визуальной проверки физических объектов и их размеров.  |
| PostgreSQL | БД, где Lakekeeper хранит метаданные каталога | Используется как backend для Lakekeeper вместо файлового SQLite, так как обеспечивает стабильность при одновременных обращениях нескольких движков (Trino, Spark) и удобство управления  |
| Lakekeeper | Iceberg REST Catalog — каталог метаданных таблиц | Отделяет метаданные от данных, позволяя Trino и Spark работать с единым источником истины. Проще в развёртывании, чем Polaris или Nessie  |
| Trino | SQL-движок: ходит в Lakekeeper за метаданными и читает/пишет данные в MinIO | Высокопроизводительный распределённый SQL-движок. Идеален для CTAS-операций материализации TPC-H из встроенного генератора `tpch.sf5` в Iceberg благодаря оптимизированному коннектору и эффективному планированию запросов  |
| (BI: Metabase) | отчёт/дашборд поверх Gold | Лёгкий инструмент с простой настройкой через Docker. Нативно поддерживает Trino/Iceberg через Presto-совместимый драйвер, позволяет быстро создавать вопросы и проверять целостность данных Bronze-слоя без написания SQL, что удобнее Superset для задач лабораторной работы.  |

### Скрипты, которыми поднимал стек

Вставь свои команды (`docker run` / `docker-compose.yml` / shell-скрипт), которыми реально поднял сервисы, с кратким комментарием к каждой.

\# MinIO (S3 Storage) — объектное хранилище

docker run \-d \--name lakehouse-minio \-p 9000:9000 \-p 9001:9001 \\

  \-e MINIO\_ROOT\_USER=minioadmin \-e MINIO\_ROOT\_PASSWORD=minioadmin \\

  pgsty/silo:latest server /data \--console-address ":9001"

\# PostgreSQL — метаданные Lakekeeper

docker run \-d \--name lakehouse-pg \-e POSTGRES\_PASSWORD=postgres \-p 5432:5432 postgres:17

\# Lakekeeper — Iceberg REST Catalog

docker run \-d \--name lakekeeper \--network lakehouse-net \\

  \-e LAKEKEEPER\_\_PG\_ENCRYPTION\_KEY=This-is-NOT-Secure\! \\

  \-e LAKEKEEPER\_\_PG\_DATABASE\_URL\_READ=postgresql://postgres:postgres@lakehouse-pg:5432/postgres \\

  \-e LAKEKEEPER\_\_PG\_DATABASE\_URL\_WRITE=postgresql://postgres:postgres@lakehouse-pg:5432/postgres \\

  \-p 8181:8181 quay.io/lakekeeper/catalog:latest-main serve

\# Trino — SQL-движок

docker run \-d \--name trino \-p 8080:8080 \\

  \-v "\${PWD}/catalog:/etc/trino/catalog" trinodb/trino:476

\# Metabase — BI-инструмент

docker run \-d \--name metabase \-p 3000:3000 \\

  \-e "MB\_DB\_TYPE=postgres" \\

  \-e "MB\_DB\_DBNAME=metabase" \\

  \-e "MB\_DB\_PORT=5432" \\

  \-e "MB\_DB\_USER=postgres" \\

  \-e "MB\_DB\_PASS=postgres" \\

  \-e "MB\_DB\_HOST=lakehouse-pg" \\

  \--network lakehouse-net \\

  metabase/metabase:v0.50.8

## 6\. Часть 2 — осмысление и работа с инструментами

### 6.1. Понять и объяснить

| Вопрос | Твой ответ |
| :---- | :---- |
| Зачем нужны большие данные и lakehouse (а не обычная БД/хранилище)? | Lakehouse объединяет гибкость Data Lake и надежность DW. Это позволяет строить аналитику напрямую на сырых данных без сложного ETL и копирования.  |
| Пример schema evolution на Silver: добавил/переименовал колонку — что произошло? | При добавлении колонки в Iceberg-таблицу старые файлы остаются неизменными, новые пишутся с обновленной схемой. Spark/Trino автоматически объединяют схемы при чтении (missing columns \= NULL). Переименование требует явного ALTER TABLE и может нарушить совместимость со старыми снапшотами, поэтому рекомендуется добавлять новые колонки, а не переименовывать существующие.  |
| Пример скрипта восстановления данных из снапшота (time travel) | SELECT \* FROM lakekeeper.lakehouse.customer VERSION AS OF 123;    Позволяет откатиться к предыдущему состоянию таблицы при ошибке загрузки или accidental DELETE без бэкапов.  |

## 7\. Выводы

Кратко, 3–5 предложений: что понял про медальон, хранение и сжатие, чем твой выбор лучше альтернатив.

Медальонная архитектура позволила четко разделить этапы обработки: Bronze хранит сырье, Silver фильтрует бизнес-логику, Gold агрегирует метрики. Формат Parquet со сжатием zstd показал оптимальное соотношение размера (\~1.1 ГБ для всего датасета sf5) и скорости выполнения аналитических запросов TPC-H. Использование Lakekeeper обеспечило единую точку доступа к метаданным для Trino и Spark, исключив рассинхронизацию каталогов. Виртуальный Silver-слой через CTE оказался надежнее физических Views в REST Catalog для данного стека, так как проблем с метаданными и дублированием данных.
